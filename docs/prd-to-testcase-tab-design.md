# PRD 转测试用例 Tab 设计方案

## 1. 方案结论

在现有一级导航中新增 **「PRD 转用例」** Tab，放在「用例管理」前面。

推荐采用“**Web 页面 + 持久化生成任务 + 独立 QA Worker + 只读版本化 Skill + 可视化用例审查 + 审查通过后直接同步用例管理**”的架构：

```text
上传 PRD
  -> 解析为标准 Markdown 和附件清单
  -> AI 按 QA Skill 生成执行画像、蓝图和结构化用例 spec
  -> QA Skill 脚本检索知识、生成 Excel、执行门禁
  -> 回读最终 Excel，生成同哈希的可视化审查快照
  -> 对应审查人员在线查看、批注、驳回或通过
  -> release_acceptance 单一准出
  -> 审查通过后直接同步到用例管理
```

不建议让前端直接调用 `casegen.py`。该脚本只会把已经准备好的蓝图和 spec 转成用例，PRD 理解、风险识别、蓝图、结构化 spec、覆盖判定和人工语义复核仍需要编排层完成。

## 2. 已确认的现状与约束

### 2.1 当前平台

- 前端是单页应用，一级导航和路由集中在 `frontend/index.html`、`frontend/app.js`。
- 后端是本地 `ThreadingHTTPServer`，接口集中在 `frontend/server.py`。
- 现有长任务已经有任务状态落盘、后台线程、取消、恢复和进程检查机制，可以复用设计模式。
- 请求体当前使用 JSON，最大 50 MB；现有 Excel 上传采用 Base64。
- 当前便携版承诺无需用户安装 Python，因此正式方案不能依赖系统 `python.exe`。
- 当前模型配置和连通性检查可直接复用，不另建一套 API Key 配置。

### 2.2 QA Skill

- 大小：1,029,185 bytes
- SHA-256：`FFDF484A2F24F30A7A9CAD757F8545F4ECEC2F990B5DE9768A6BB9EA93DB6DBA`
- 快照日期：2026-08-25

Skill 的权威生产入口是：

关键合同：

- 普通任务默认 `auto -> core`，只有命中风险或用户明确要求时升级能力包/strict。
- 核心结构门禁是 S1-S36；启用多平台覆盖时增加 S37。
- 措辞、归类、顺序、功能边界是不可省略的四项人员执行质量复核。

### 2.3 与现有用例库的兼容问题

当前 Excel 导入器会读取“模块/Sheet、用例编号、测试项、测试点、前置、步骤、预期”等字段，但没有保存 Skill 要求的“功能点”，还会给执行映射补默认值。

生成完成后不立即写入正式用例库，而是先走可视化审查；审查通过后可从当前页面直接同步。正确链路是：

1. QA 工作区中的 15 列 Excel 是生成阶段的权威产物。
2. 后端重新打开该 Excel，按合并单元格继承规则生成同哈希的 `review-snapshot.json`，供页面完整展示。
3. 对应人员在审查页面查看用例、留下问题或提交审查通过。
4. 审查通过并完成最终准出后，页面开放“同步到用例管理”按钮。
5. 专用同步适配器保留功能模块、功能点、测试项、测试点和稳定 ID，并在事务完成后读回核对。
6. 新同步用例的自动化映射状态固定为 `UNMAPPED`，不能冒充已固化或可直接执行。

## 3. 页面设计

### 3.1 导航与路由

- 导航名称：`PRD 转用例`
- 实现路由：`/prd-cases`
- 一级导航顺序：项目总览 → PRD 转用例 → 用例管理 → 自动化执行 → 测试报告 → ONES 缺陷 → 环境中心 → 蓝牙工作台
- 现有 `/tests` 继续兼容原用例管理入口；新功能使用独立 `/prd-cases`。

### 3.2 页面结构

页面内分三个子页签：

#### A. 生成任务

顶部“新建生成任务”区：

- 目标项目：默认当前全局项目，可切换。
- PRD 文件：首版支持 `.docx`、`.md`、`.txt`；PDF/扫描件列为后续增强。
- 补充材料：可选，多文件；用于补充交互说明、图片或历史约束。
- 产品形态：默认自动识别，允许用户覆盖。
- 适用平台：Android、iOS、固件、设备等，可多选。
- 执行模式：默认 `auto`；高级选项允许 `core`、`strict`。
- 补充说明：纯文本，不作为文件路径或命令执行。
- 主按钮：`开始生成`。

任务开始前展示预检：

- 模型服务是否可用。
- Skill 包版本和哈希是否有效。
- 文件类型、大小和可解析性。
- 目标项目是否存在。

任务详情区：

- 当前阶段和总进度。
- 已识别模块、平台、主要风险和启用的能力包。
- 实时事件日志，只展示业务事件，不泄露密钥和完整内部提示词。
- 待确认问题，支持用户填写后继续。
- 取消、失败后重试、服务重启后继续。
- 产物下载：原始 PRD、标准化 PRD、执行画像、用例 Excel、门禁报告、准出清单。

任务历史表：

- 项目、PRD 名称、Skill 版本、模型、模式、状态、用例数、创建时间、最终准出。
- 支持查看、继续、下载和归档，不提供直接物理删除入口。

#### B. 用例审查

生成完成并通过机械门禁后，任务在 `/prd-cases?job=<job_id>` 展示审查内容。审查页面不是简单展示 Excel 文件名，而是提供完整的在线用例表：

- 左侧模块树：`功能模块 > 功能点 > 测试项`，显示各层用例数和问题数。
- 右侧用例表：展示用例编号、测试点、前置条件、操作步骤、预期结果、优先级、平台、版本、方式、备注和待确认项。
- 表头和模块/功能点列固定；大用例集采用虚拟滚动或服务端分页，不能一次把数千行塞进 DOM。
- 支持按模块、功能点、测试项、优先级、平台、待确认、风险和审查状态筛选。
- 支持关键词搜索、展开长步骤、只看有意见的用例和跳转下一问题。
- 页面顶部固定显示：PRD 文件、Excel SHA-256、Skill 版本、用例数、门禁结果和当前任务状态。
- 可下载当前任务的 Excel，但页面展示必须来自该 Excel 的回读快照，二者哈希完全一致。

每条用例支持审查操作：

- `通过本条`：确认当前用例无问题。
- `提出问题`：选择措辞、归类、顺序、功能边界、步骤/预期、遗漏、重复或其他问题，并填写意见。
- `批量通过当前筛选结果`：只允许对当前明确可见的筛选集合操作，记录筛选条件和数量。
- `退回修改`：任务进入 `REJECTED`，生成端按问题重新调用生成器、导出 Excel 并重跑质量门禁。
- `审查通过`：只有全部阻断问题已关闭、待确认已处理、Excel 哈希未变化且四项 P0 复核完成时可点击。

审查页按 Skill 的四个 P0 维度提供全表复核清单：

- 措辞：测试点是否是可判定的“验证……”意图。
- 归类：功能模块、功能点、测试项是否属于正确业务边界。
- 顺序：模块内是否按真实用户主流程连续组织。
- 功能边界：跨功能/中断场景是否归到被影响业务，而不是归到触发源。

审查决定必须记录审查人、时间、整体/逐条意见和 Excel SHA-256。

当前平台只允许本机访问且没有人员账号体系，首版要求审查人填写姓名/工号并留痕；如果以后让其他电脑通过链接审查，必须先增加登录、权限和审查人身份认证，不能直接放开监听地址。

用户提交审查通过后才允许执行最终 `release_acceptance`。未完成审查时可以下载草稿 Excel，但状态必须保持 `NO_GO + DRAFT`。

#### C. 同步记录

审查通过且最终准出为 GO 后，在审查页和同步记录页同时开放 **“同步到用例管理”**：

- 目标项目在创建生成任务时已经确定，默认不允许同步时临时换项目。
- 点击后先展示同步摘要：新增、生成新版本、冲突、跳过和失败数量。
- 无冲突时可直接确认同步；有编号或稳定 ID 冲突时必须选择“生成新版本”或“跳过”，禁止静默覆盖。
- 同步采用事务和幂等键；重复点击或网络重试不能产生重复用例。
- 同步完成后立即从用例管理数据库读回，核对稳定 ID、字段、数量和来源哈希。
- 成功后提供“前往用例管理”按钮，并按本次同步批次过滤展示。
- 同步记录保存目标项目、审查决定、Excel SHA-256、同步批次、结果摘要和失败明细。

## 4. 生成、审查、同步与准出状态

生成状态、审查状态、同步状态和 QA 准出状态必须分开，避免“Excel 已生成”“人员已通过”和“已经进入用例管理”混成一个绿色对勾。

### 4.1 生成状态

```text
QUEUED
  -> PARSING
  -> ANALYZING
  -> RETRIEVING
  -> GENERATING
  -> VALIDATING
  -> BUILDING_REVIEW_SNAPSHOT
  -> GENERATED
```

分支状态：

- `WAITING_INPUT`：缺少会改变结论的参数或 PRD 存在真实 Blocker。
- `CANCELLED`：用户主动取消。
- `INTERRUPTED`：服务退出或 Worker 丢失，可按阶段恢复。
- `FAILED`：不可恢复错误；保留日志和已完成产物。

### 4.2 审查状态

```text
UPLOADED -> GENERATING -> READY_FOR_REVIEW -> APPROVED
                       \-> QUALITY_BLOCKED   \-> SYNCED
                       \-> FAILED             \-> SYNCED_WITH_CONFLICTS
READY_FOR_REVIEW -> REJECTED -> GENERATING -> READY_FOR_REVIEW
```

- 任一源 PRD、Excel 或审查快照变化，旧 `APPROVED` 不能继续同步，必须重新生成和审查。
- `APPROVED` 必须绑定审查记录与 Excel SHA-256。

### 4.3 同步状态

```text
READY_FOR_REVIEW -> APPROVED -> SYNCED
                            \-> SYNCED_WITH_CONFLICTS
```

- 只有任务状态为 `APPROVED` 且最终准出为 GO 时才允许同步。
- 同一任务重复同步直接返回原同步结果，不重复创建已成功写入的用例。

### 4.4 QA 状态

沿用 Skill 合同：

- `NO_GO + DRAFT`：生成失败、质量门禁阻断或人工驳回。
- `NO_GO + READY_FOR_REVIEW`：Excel 回读和质量门禁通过，等待人工审查。
- `GO + READY_WITH_RISKS`：本机人工审查通过，可同步用例管理。

首版不宣称 `STRICT_GO`；完整严格准出属于后续增强。

`GENERATED`、`APPROVED`、`SYNCED` 也不能替代上述 QA 状态，页面必须分别展示。

## 5. 后端架构

### 5.1 推荐模块

```text
src/agent_loop_system/qa_generation/
├── models.py              请求、状态、结构化 LLM 输出模型
├── repository.py          任务状态、事件和产物索引落盘
├── service.py             创建、查询、取消、恢复任务
├── worker.py              独立 Worker 入口和阶段编排
├── prd_parser.py          DOCX/PDF/Markdown/TXT 标准化
├── skill_bundle.py        Skill 校验、解包、版本和只读边界
├── orchestrator.py        AI 阶段、知识检索、脚本门禁编排
├── review.py              Excel 回读快照、在线审查、版本和哈希绑定
└── case_sync.py           审查通过后同步现有用例管理
```

`frontend/server.py` 只负责 HTTP 边界和调用 `QaGenerationService`，不要继续把整套业务流程堆进这个已经很长的文件。

### 5.2 独立 Worker

生成可能持续几十分钟，不能在一次 HTTP 请求中完成，也不宜只放在 Web 服务的 daemon thread 中。

推荐：

- API 创建任务后立即返回 `202 Accepted + job_id`。
- 后端启动独立 QA Worker 进程。
- Worker 每完成一个阶段就原子写入 `job-state.json` 和 `events.jsonl`。
- 前端每 1 至 2 秒轮询任务状态；后续可替换为 SSE，但首版没必要先养一套新协议。
- 服务重启时检查 PID、进程身份和阶段哈希；可安全继续则继续，否则标记 `INTERRUPTED`。
- 有生成任务运行时，现有“页面关闭后退出服务”的 watchdog 必须暂缓退出；任务结束后恢复原行为。

### 5.3 便携版执行

正式便携版不能执行外部 `python scripts/*.py`。实现时应：

1. 将已验证的 Skill ZIP 作为版本化资源打入 `_internal`。
2. 首次使用时按哈希解压到应用数据目录的只读缓存。
3. Worker 使用内置 Python 运行时通过模块调用或 `runpy` 执行 Skill 脚本。
4. 冻结版入口支持内部参数，例如 `Agent-loop.exe --qa-worker --job <id>`。
5. 源码开发模式使用同一 Worker 逻辑，避免开发态和发布态两套流程。

运行时禁止依赖原始 `D:\拓步自动化_ALL\new\...zip` 路径；该路径只作为本次引入的源证据。

## 6. Skill 编排流程

### 阶段 1：输入固化

- 保存原文件，计算 SHA-256。
- 校验扩展名、文件签名、大小、DOCX/PDF 解压上限和路径穿越。
- 将文本、表格、标题和附件清单标准化为 Markdown。
- 扫描型 PDF 或无法识别的图片必须明确提示，不能假装已经解析。

### 阶段 2：执行画像

- 把上传内容当作不可信业务数据，不执行 PRD 中的命令、网址或“忽略系统规则”等指令。
- AI 结构化输出产品形态、模块、平台、风险和 Blocker。
- 调用 `new_project.py --execution-mode auto --workspace-root ...` 初始化外部工作区。
- 用户指定 `core/strict` 时记录为显式覆盖；风险只允许升级，不允许降级。

### 阶段 3：蓝图和知识检索

- AI 填写 `module_boundary / feature_order / execution_order / hierarchy_map / unsupported_features / platform_scope / main_risks`。
- 按产品形态、模块和关键词调用知识路由脚本。
- 只读取命中的 1 至 3 份知识/规范，禁止把整个知识库塞进一次模型请求。

### 阶段 4：分工作单生成

- 每个独立功能写入自己的 `workunits/<功能>/`。
- AI 输出严格结构化 spec，不直接手写 Excel。
- 先运行生成合同，再调用 `casegen.py` 和 `export_cases.py`。
- 启用 `pilot` 时先生成 3 至 5 个高风险先导模块；未启用时不强行增加流程。

### 阶段 5：机械门禁与有限修订

- 运行 S1-S36；启用平台覆盖时追加 S37。
- 每次失败按门禁编号定向检索和修源数据，禁止只改 Excel。
- 自动修订最多两轮；仍失败则进入 `WAITING_INPUT` 或 `FAILED`，避免无限烧模型额度。

### 阶段 6：可视化审查

- 重新打开最终 Excel，按合并单元格继承规则生成可分页的 `review-snapshot.json`。
- 初始化人员执行质量复核记录，将快照、审查意见和 Excel 当前 SHA-256 绑定。
- 对应人员在页面逐条或按明确筛选范围审查，完成四项 P0 复核和分层抽样。
- 审查意见落到稳定 ID，不依赖容易变化的展示行号。
- 退回修改时只修改源 spec，重新导出并重跑受影响门禁；重新导出后旧审查自动失效。
- 审查通过后由 `release_acceptance.py` 产生单一准出结论。

### 阶段 7：同步用例管理

- 只接受 `APPROVED + GO` 且 Excel、审查快照和准出报告哈希一致的任务。
- 生成同步预览，明确新增、新版本、冲突和跳过。
- 使用专用映射保留完整层级、稳定 ID、来源任务和来源哈希。
- 在单个事务中写入用例管理；失败时回滚，成功后读回核对。
- 同步成功不等于自动化可执行，新用例映射状态保持 `UNMAPPED`。

## 7. API 草案

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/api/prd-cases/jobs` | 新建任务，返回 202 |
| `GET` | `/api/prd-cases/jobs` | 按项目查询任务历史 |
| `GET` | `/api/prd-cases/jobs/{job_id}` | 查询状态、进度、风险和产物 |
| `GET` | `/api/prd-cases/jobs/{job_id}/cases` | 查询最终 Excel 的回读审查快照 |
| `GET` | `/api/prd-cases/jobs/{job_id}/download` | 下载生成的 Excel |
| `POST` | `/api/prd-cases/jobs/{job_id}/review` | 驳回或审查通过，并提交逐条/整体意见 |
| `POST` | `/api/prd-cases/jobs/{job_id}/regenerate` | 按审查意见重新生成 |
| `POST` | `/api/prd-cases/jobs/{job_id}/sync` | 审查通过后直接同步用例管理 |

首版可沿用 Base64 JSON 上传以减少对现有服务器的改动，原文件建议限制为 20 MB。若后续支持大型扫描 PDF，再单独实现流式 multipart 上传。

```text
│   ├── review-snapshot.json    最终 Excel 的规范化回读数据

│   ├── review-decision.json    审查人、结论、版本与 Excel 哈希
│   └── review-ledger.json      四项 P0 复核和分层抽样账本
├── sync/
│   ├── sync-preview.json
│   └── sync-result.json
└── artifacts.json              文件名、类型、SHA-256、生成阶段
```

每个任务必须记录：

- 原始 PRD 哈希。
- Skill ZIP 哈希和快照版本。
- 模型名称、提示词版本和执行模式。
- 各阶段输入/输出哈希。
- 最终 Excel 哈希、审查快照哈希、门禁结果、审查人员、审查决定、同步批次和准出结论。

不得记录 API Key、完整认证头或包含密钥的环境变量。

## 9. 审查通过后直接同步用例管理

审查通过后不需要审查人员重新下载、再去用例管理上传同一份 Excel。页面直接调用专用同步接口；该接口使用已审查并绑定哈希的结构化快照，不复用当前会丢字段的通用 Excel 解析器：

| Skill 字段 | 平台字段/处理 |
| --- | --- |
| 功能模块 | `sheet/module` |
| 功能点 | 新增 `feature_point` |
| 测试项 | `test_item` |
| 测试点/检查项 | `test_point` |
| 前置条件 | `precondition_text` |
| 操作步骤 | `steps_text` |
| 预期结果 | `expected_text` |
| 优先级 | `priority` |
| 稳定 ID | `stable_id`，与 `case_id` 一致且不可因排序改变 |
| 用例编号 | `case_id`，冲突时走预览和新版本策略 |
| 来源任务 | `source_ref.job_id` |
| 来源审查 | `source_ref.reviewer`、`source_ref.reviewed_at`、`source_ref.workbook_sha256` |
| 自动化映射 | 初始固定 `UNMAPPED` |

同步规则：

1. 同步资格必须同时满足任务状态 `APPROVED`、`release.decision=GO` 和工作簿/审查哈希一致。
2. 同一任务同步后持久化原结果；重复调用直接返回该结果，不重复写入。
3. 已存在相同稳定 ID 且内容变化时创建用例新版本，不覆盖历史版本。
4. 稳定 ID 与用例编号分别冲突时进入冲突清单，必须显式处理。
5. 同步前展示新增、新版本、冲突、跳过、待确认数量；同步后读回数据库核对字段、数量和来源哈希。
6. 同步成功后自动跳转或提供链接到 `/cases?project=<目标项目>&source_batch=<同步批次>`。

## 10. 安全与可靠性

- 只允许本机 loopback 访问，沿用当前服务边界。
- 文件名只保留展示名；物理路径使用服务生成的安全 ID。
- DOCX 按 ZIP 炸弹规则限制总解压大小、条目数和压缩比。
- PDF 页数、文本长度、图片数量和单页渲染大小设上限。
- PRD 内容永远作为数据传给模型，不允许改变系统规则、调用工具或指定写入路径。
- Skill 缓存只读，任务只能写自己的工作区。
- 取消时终止经过进程身份校验的 Worker，不按模糊进程名批量杀进程。
- 每阶段原子落盘；服务重启后不得沿用哈希不一致的下游结果。
- 审查快照只从最终 Excel 回读生成，不能由前端自行拼装；同步也只接受该快照。
- 审查意见按稳定 ID 绑定；显示行号和排序变化不能把意见串到另一条用例。
- 审查通过后文件一旦变化，审查、准出和同步资格立即失效。
- 模型调用设置超时、有限重试、模块级并发上限和任务级预算上限。
- UI 显示待确认和剩余风险，不用用例条数包装“完整覆盖”。

## 12. 验收标准

### 功能验收

- 用户可在新 Tab 上传 PRD，刷新或切换页面后任务仍可查询。
- 一份有效 PRD 能生成可下载的标准 Excel、执行画像和门禁报告。
- Excel 生成后能在页面按完整固定层级展示全部用例，页面行数、字段内容和 Excel 回读结果一致。
- 审查人员可筛选、逐条查看、提交意见、退回修改或审查通过，所有意见绑定稳定 ID。
- 缺参数、扫描 PDF、模型不可用、Skill 损坏都有明确可行动提示。
- 取消、重启、恢复不会出现两个 Worker 同时写同一任务。
- 人工复核前不能出现 GO；修改 Excel 后旧复核和旧准出自动失效。
- 审查通过且 GO 后可直接同步用例管理；同步前可预览，重复操作不产生重复数据。
- 同步后功能点、稳定 ID、来源审查信息和来源 Excel 哈希不丢失，自动化状态保持 `UNMAPPED`。

### 回归验收

- 原有 `/overview`、`/cases`、`/runs`、`/reports`、`/defects`、`/environments`、`/bluetooth` 路由不受影响。
- 一级导航固定为“项目总览 → PRD 转用例 → 用例管理 → 自动化执行……”。
- 原 Excel 导入、用例执行、报告导出和便携版启动行为保持通过。
- Windows 中文路径、空格路径和无系统 Python 环境通过实机验证。
- 发布包中不包含客户 PRD、生成工作区、密钥、缓存或外部绝对路径。

## 13. 推荐实施决策

首版直接交付 **P0 + P1 的完整业务闭环**：

```text
上传 PRD -> Skill 生成 Excel -> 可视化用例审查 -> 退回/通过 -> 最终准出 -> 直接同步用例管理
```

扫描 PDF、跨电脑审查、人员指派和严格多上下文评审可以后置，但“看得到全部用例、能审查、通过后能同步”不能再拆到后续版本，否则这个 Tab 仍只是一个文件生成器，不是实际工作台。

这样既能尽快形成可用功能，也不会为了赶一个 Tab，把 QA Skill 最重要的质量边界削成一层好看的按钮。
